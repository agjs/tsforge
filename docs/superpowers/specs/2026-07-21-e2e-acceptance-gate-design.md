# End-to-End Acceptance Gate — Design

**Status:** approved design (pending spec review) → next: implementation plan via writing-plans.

**Goal:** Close the gate-parity hole that let build19 reach "GREEN, 4/4 verified" with three of four features having a hollow UI. Add a harness-owned, plan-derived, **browser end-to-end** acceptance gate that drives real CRUD through the actual running UI and blocks feature-verify unless the feature is genuinely usable.

**Architecture (2-3 sentences):** Core derives an abstract, stack-agnostic acceptance spec from the approved `IProductPlan`. The BoringStack seam turns that spec into a Playwright suite generated into the app's own `e2e/` dir and run via the app's installed `@playwright/test`, reusing the app's existing auth fixtures. The build loop runs the suite per-slice (gating verify) and at final acceptance (full relational chain), turning failures into targeted steers.

**Tech stack:** TypeScript, Bun, Elysia (API), React + generated api-client (UI), Drizzle/Postgres, `@playwright/test` 1.61.1 (already in the BoringStack scaffold, with `playwright.config.ts`, an `e2e/` suite, page objects, and `authedPage`/`testUser` fixtures).

## Global Constraints

- **Core stays stack-agnostic.** No BoringStack strings, paths, or Playwright in `packages/core/src/loop/*` (the generic loop). All stack specifics live under `packages/core/src/loop/boringstack/`. (HARD — see memory `core-must-stay-stack-agnostic`.)
- **Never relax the gate.** This ADDS a required gate; it removes/loosens nothing. The existing fast gate (compile + lint + size + knip + model tests) stays exactly as-is.
- **Harness-owned, not model-authored.** Acceptance criteria derive from the plan and are executed by code the model cannot edit. The generated E2E spec lives at a path outside the model's editable scope, and is regenerated by the harness each run (a model edit to it is discarded).
- **Behavioral, not structural.** Proof is "fill form → row appears → reload → still there → edit → delete," not "a testid exists." Testids are only stable addressing.
- **Flag-gated.** Behind `TSFORGE_NO_E2E_ACCEPTANCE` kill-switch; default ON once validated. Every core-loop change carries tests pinning the other paths (unified-escalation/steer/checkpoint/fingerprint/session-gate/boringstack-build) unchanged.
- **Flake ≠ failure.** A behavioral assertion failure is a feature red (→ steer). A browser-won't-launch / infra timeout is an infra-abort (see #47), never a feature red. Bounded retries separate the two.

## Why (evidence)

build19 (4-slice relational CRM Company→Contact→Deal→Activity) reached GREEN, "4/4 features verified," whole-app final acceptance GREEN. Three independent audits (direct file read + code-audit agent + 4-model reviewer panel from the log alone) converged:

- **API:** real CRUD for all 4 (Drizzle insert/select/update/delete, user-scoped, real FKs + cascade).
- **UI:** only **Company** is usable. **Contact/Deal/Activity** pages render only a title + loading/empty `<p>`; they pull `{isLoading, showEmpty}` and ignore `items` and every CRUD handler. Contact has no form/row components; Deal/Activity have full hooks/handlers that are orphaned. Mutations pass `knip` only because their own `*.mutations.test.tsx` reference them (test-only usage hides dead production code). None of the 4 are in the sidebar nav.
- **Root cause:** final acceptance == the per-feature fast gate (compile + lint + size + knip + model-authored unit tests). No integration/E2E. A hollow app passes. (`build.ts:42` already names this "a gate-parity hole (4/4 panel).") Panel's unanimous fix: a harness-owned suite that boots + auths + drives CRUD through the real UI for every resource, links them, verifies persistence — required for verify.

## Non-goals

- Not replacing model-authored tests (they stay; this is additive).
- Not a general visual-regression / a11y / performance suite (that is separate, e.g. the scaffold's own `visual.spec.ts`/lighthouse).
- Not interpreting arbitrary free-text plan rules with an LLM in v1 (negative cases are derived from field types + structured `mustNotHappen` heuristics; richer prose interpretation is a fast-follow).

## Components

### 1. Selector contract (the seam between generic runner and stack UI)

A fixed, plan-derivable set of `data-testid`s the generated feature UI must expose. Derived deterministically from `entity.id` (camelCase) + role. For entity `e` with fields `f…` and relationships `belongsTo P` (FK `pId`):

| testid | element |
|---|---|
| `nav-{e}` | sidebar nav link to the feature |
| `{e}-list` | list/table container |
| `{e}-empty` | empty-state element |
| `{e}-row` | each row (repeated) |
| `{e}-row-{f}` | a displayed cell for field `f` (for the plan's `ui.shows`) |
| `{e}-create` | button that opens/reveals the create form |
| `{e}-form` | the create/edit form |
| `{e}-field-{f}` | input for field `f` |
| `{e}-field-{pId}` | select/combobox for a relationship parent |
| `{e}-submit` | form submit button |
| `{e}-row-edit` / `{e}-row-delete` | per-row edit / delete controls |
| `{e}-confirm-delete` | delete confirmation control |

- **Generated by core** (generic string derivation from the plan) and handed to the seam + surfaced to the model as a convention/guide (the BoringStack refine-prompt / conventions seam, NOT hardcoded in core).
- **Enforced by a change-scoped meta-rule** (seam): a feature shipping a page/list/form must expose the required testids. This guides the model to add them; the behavioral E2E then proves they're wired (closing the "testid on an empty div" gap).
- Company already implements list/row/edit/delete/form *behaviorally* — it simply lacks the testids; the contract is largely a naming discipline over what a correct feature already renders.

### 2. `IAcceptanceSpec` derivation (core, stack-agnostic)

Pure function `planToAcceptanceSpec(plan: IProductPlan): IAcceptanceSpec`. No stack strings.

```
IAcceptanceSpec { entities: IEntityAcceptance[] }
IEntityAcceptance {
  id: string                       // entity.id (PascalCase)
  key: string                      // camelCase testid root
  nav: string                      // plan ui.nav (nav label to click)
  fields: IAcceptField[]           // name, type, optional, a valid sample value, invalid sample value(s)
  shows: string[]                  // plan ui.shows — cells asserted in the list
  screens: ("list"|"detail"|"form"|"dashboard")[]
  parents: { entity: string; fkField: string }[]  // from relationships "belongsTo X"
  negatives: INegativeCase[]       // derived: missing-required, bad-email (email-named/typed field),
                                   //   negative-number (numeric field), plus structured mustNotHappen
  acceptanceCheck: string          // plan verification.acceptanceCheck (human-readable, logged)
}
```

Value generation is deterministic (seeded off the entity index, since `Math.random`/`Date.now` are unavailable in the loop's reproducible paths) so runs are repeatable.

### 3. E2E generator (BoringStack seam)

`IAcceptanceSpec` → a Playwright spec written to `apps/ui/e2e/_acceptance/{key}.spec.ts` (harness-owned path; regenerated each run, excluded from the model's editable scope and from knip/normal test entries). Reuses the app's `authedPage` fixture for a logged-in browser and `testUser`/API helpers for provisioning.

Per entity, the generated spec asserts (each an independent test so failures attribute precisely):

- **nav+list:** from `/dashboard`, click `nav-{e}`; land on the feature route; `{e}-list` (or `{e}-empty`) is present.
- **create → appears:** click `{e}-create`; fill each `{e}-field-{f}` with the valid sample (relationship selects: choose a pre-seeded parent by label); click `{e}-submit`; assert a new `{e}-row` containing the `shows` values appears.
- **persist:** reload; assert the row is still present (proves real API persistence, not local state).
- **update:** `{e}-row-edit` → change a field → save → assert the changed value shows and persists across reload.
- **delete:** `{e}-row-delete` → `{e}-confirm-delete` → assert the row is gone and stays gone after reload.
- **negatives:** for each `INegativeCase`, submit the invalid input and assert an error is shown AND no row is created (catches build19's Deal `amount`/`stage` and any unenforced `mustNotHappen`).
- **relationship linkage:** for child entities, seed a parent, assert `{e}-field-{fkField}` offers it, create the child against it, and assert the list shows the parent linkage (`{e}-row-{fkDisplay}`).

### 4. Auth / seed (seam)

Reuse the app's existing `authedPage` fixture (logged-in on `/dashboard`) and `testUser` (API-provisioned, worker-scoped). A **fresh user per acceptance run** for tenant isolation and repeatability. Parents for relationship flows are seeded via the API (fast, deterministic) before the child's UI flow.

### 5. Wiring (core loop + seam)

- **Per-slice:** in `build.ts`, after a feature's fast gate goes green (around the verify point, ~L253-284) and before it is marked verified, run that entity's acceptance suite (its own CRUD/UI + negatives + linkage to already-built parents). **Verify only if it passes.**
- **Final acceptance:** extend the existing final-acceptance block (~L486-514, currently "full validate + build + size checks") to append the full suite for all entities plus the **full relational chain** (create Company → Contact under it → Deal under both → Activity under the Deal, each through the UI, asserting linkage end-to-end).
- **Failure → steer:** an acceptance failure produces a structured, targeted steer identifying the failed step and the exact expectation, e.g. *"Contact acceptance failed at CREATE: opened `/contact` via nav, clicked contact-create, filled the form, submitted; expected a contact-row with name 'Ada' — none appeared. Wire the create mutation to the form's submit and render the query items in contact-list."* Fed back to the loop like any gate error (via the BoringStack refine-prompt seam), so the model fixes the hollow feature. A rollback/checkpoint is NOT triggered by acceptance (it is a verify gate, not a near-green count signal).
- **Flake handling:** bounded retries (e.g. 2) on the whole entity suite. Persistent assertion failure → feature red + steer. Browser-launch / connection failure → infra-abort path (#47), surfaced as infra, not a feature red.

## Data flow

```
approved IProductPlan
   │  planToAcceptanceSpec()            [core, generic]
   ▼
IAcceptanceSpec ──► generateE2E()       [boringstack seam]
   │                     │ writes apps/ui/e2e/_acceptance/{key}.spec.ts
   │                     ▼
   │              app `playwright test` (reuses authedPage/testUser fixtures)
   │                     │ per-step pass/fail
   ▼                     ▼
build.ts verify hook ◄── IAcceptanceResult { entity, step, ok, detail }
   │  pass → mark verified
   │  fail → steer(detail) → loop fixes → re-gate → re-accept
   ▼
final acceptance: all entities + full relational chain
```

## Constraints & blast radius

- Core-loop touch points (`build.ts` verify + final acceptance) run on the BoringStack build path only; the generic loop (`turn.ts`/`session.ts`) is untouched. Still, add tests pinning the fast-gate/verify behavior unchanged when the flag is off.
- The generated `e2e/_acceptance/**` is excluded from the model's write scope (`setScope`), from knip entries, and from the fast gate's test run (it needs the booted stack + browser; it runs only at the acceptance step).
- Latency: adds tens of seconds per slice-verify + a larger final run. Accepted (correctness over speed; memory `correctness-over-speed`).
- The `run` shell tool can still mutate files; acceptance is best-effort against a cooperative model, but regenerating the spec each run + path-scoping makes gaming hard.

## Phasing (also the implementation task order)

1. **Spec derivation + selector contract.** `planToAcceptanceSpec` (core, pure, unit-tested) + deterministic testid derivation + push the contract via the conventions/refine seam + the change-scoped testid meta-rule (seam).
2. **Single-entity E2E.** Generator emits the CRUD + persistence + negative spec for one entity; run it via the app's Playwright against the booted stack; parse results to `IAcceptanceResult`.
3. **Relationships + full chain.** Parent seeding + child linkage flows + the final whole-app chain spec.
4. **Loop wiring.** Per-slice verify gating + final-acceptance extension + failure→steer + flake retries + infra-abort classification + the kill-switch flag + path-scope/knip exclusions.
5. **Validation (acceptance test of the gate itself).** Re-run build19's shape (or reset valbuild19's features): the hollow Contact/Deal/Activity MUST now go RED at verify and force the loop to wire real UI CRUD; Company (already usable) MUST pass. A build that previously false-greened must no longer be able to.

## Validation / proof

- Per task: targeted unit tests + one full `bun run validate` + `harness-review --base main`.
- End-to-end proof (Phase 5): a live build where a deliberately-hollow feature is caught at verify and driven to real usability; and a clean feature passes without false-fail across ≥3 runs (flake budget).

## Open questions / risks

- **Testid adoption cost.** The model must learn to emit the contract testids; mitigated by the convention guide + meta-rule. Risk: early builds spray on the new rule (like any new convention) — accept, then front-load the guide (memory `ws-b-count-only-and-ws-a-frontload`).
- **Playwright flake in-loop.** Mitigated by retries + infra-abort classification; monitor false-fail rate in Phase 5.
- **Negative-case fidelity.** v1 derives negatives from field types + simple `mustNotHappen` heuristics; genuinely prose-only rules may be under-covered. Fast-follow: a bounded translation step.
- **Per-slice latency compounding** on many-slice builds; if it bites, make per-slice acceptance CRUD-only and reserve the full negative+relationship matrix for final. (Decision deferred to Phase 4 data.)
