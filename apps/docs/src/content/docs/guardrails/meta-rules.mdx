---
title: Meta-rules
description: Gate checks on package.json, tsconfig, CI files, and test layout (not TypeScript source).
---

Most tsforge rules lint **`.ts` files** through ESLint. **Meta-rules** are different: they inspect **project files** that normal lint does not cover.

Think of them as housekeeping checks. Is `package.json` pinned correctly? Is `tsconfig.json` strict? Does every logic module have a colocated test file? Are GitHub Actions pinned?

They run in the same gate pass as ESLint. A meta-rule failure blocks the task the same way a type error would.

## What they look at

| Area | Example checks |
| --- | --- |
| `package.json` | exact version pins, no duplicate HTTP client libraries |
| `tsconfig.json` | strict mode on, include paths exist |
| Source text | no `@ts-ignore`, no `eslint-disable` comments |
| CI workflows | pinned action SHAs, pinned runners, job timeouts |
| Tests | service/util files have a matching `*.test.ts` sibling |

## All 10 rules today

| ID | Category | Checks |
| --- | --- | --- |
| `package-exact-deps` | supply-chain | no `^`/`~` ranges |
| `no-overlapping-libs` | supply-chain | forbid redundant libs |
| `no-eslint-disable-comments` | source-text | no inline disables |
| `no-ts-suppressions` | source-text | no `@ts-ignore` |
| `tsconfig-paths-exist` | config | include paths exist |
| `tsconfig-strict` | config | strict mode on |
| `test-sibling-required` | testing | colocated tests |
| `workflow-actions-pinned` | ci | pinned action refs |
| `workflow-runner-pinned` | ci | no `ubuntu-latest` |
| `workflow-timeout-required` | ci | job timeouts set |

## Severity

| Level | Effect |
| --- | --- |
| `error` | Gate fails. Model must fix it. |
| `warn` | Reported but gate can still pass. |
| `off` | Silenced via [tsforge.config.json](/guardrails/config/). |
