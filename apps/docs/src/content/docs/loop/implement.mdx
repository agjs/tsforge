## What problem this solves

The spec format gives us an approved task: a goal, its allowed `files:`, and an `accept:` command that defines "this chunk is done." This loop is **how one task becomes green code you can trust** — without a human watching every edit. Skip it and you're back to "the model typed something and said it's done"; you become the loop.

## What it consumes and produces

```
pre:  the run already cleared the spec's preflight gate — every service/key its
      accept:/verify needs is reachable (fail loud before building, never after)
in:   one approved task { id, type, goal, needs, files:<globs>, accept:<cmd>, covers:<A#>, docs?:<links> }
      + constitution (boringstack gate)  + the repo at the previous green checkpoint
out:  a committed, green chunk + a journal line     — or — a clean STOP with a reason
```

## The loop

```
        ┌──────────────────────────────────────────────────────────┐
        ▼                                                            │
  RED ──► EDIT ──► VALIDATE ──► (error set empty?) ──► JUDGE ──► CHECKPOINT
  write   within    tiered           │  no                 │ ok        │
  failing  files:   checks      ─────┘                     │           ▼
  tests            (structured   REPAIR (feed error-set     │      advance / pause
                    error set)    diff; loop EDIT)          │       (per autonomy)
                                      │                  reject → back to EDIT
                                      ▼
                       STALL (no progress for N)?
                                      │
            interactive ──────────────┴────────────── unattended (Ralph)
                │                                          │
          STOP + ask human                    ESCALATE: try a different approach
                                               → still stuck → NOTIFY (Slack/Discord)
                                                 + park task, move to next
```

| Step | What happens | The guarantee |
| --- | --- | --- |
| **RED** | Write the failing test(s) for this chunk; run `accept:`; **confirm it fails**. | The goalpost exists and is real *before* any implementation (a test that passes now is a bug — stop). |
| **EDIT** | Implement the chunk, touching only paths matching `files:`. | Scope is bounded; drift is detectable. |
| **VALIDATE** | Tiered: cheap scoped checks per edit; full `bun run validate` to close the chunk. Output parsed into a structured **error set**. | "Correct" is the gate's verdict, not the model's. |
| **REPAIR** | Feed the model the **error-set diff** ("2 fixed, 1 new at `x.ts:14`"); loop back to EDIT. | Validation becomes a gradient to descend, not a wall. |
| **STALL guard** | If the error set doesn't shrink for **N cycles** (or the hard cap hits): *interactive* mode stops and asks; *unattended* mode escalates to a different approach, then notifies. | No infinite thrash — and unattended, no blocking either. |
| **JUDGE** | Fresh-context pass: does this satisfy `covers:` and respect the constitution? Tries to *refute*. | Catches "passes the gate but misses the point." |
| **CHECKPOINT** | Commit the green chunk + a journal line; advance or pause per `autonomy`. | Every chunk is reviewable and revertible. |

## Test-first means unit *and* end-to-end (TDD/BDD)

The RED step is real TDD/BDD: **write the test, watch it fail, then make it pass.** The *level* of test follows the chunk's type — and a chunk may need more than one:

| Chunk type | Test written first | Style |
| --- | --- | --- |
| `[db]`, `[api]`, pure logic | unit / integration tests (real DB over mocks, per the constitution) | TDD |
| `[ui]` | component tests (render + interaction) | TDD |
| `[e2e]` | a Playwright scenario phrased as **Given/When/Then** | BDD |

So a feature ends up with a **pyramid**: many fast unit/integration tests close the logic chunks, and a few end-to-end scenarios prove the whole thing behaves. The acceptance criteria (`A#`) written in Given/When/Then map almost directly onto the e2e scenarios.

**Where the red→green signal lives — and where it doesn't.** A test is only a gate if its pass/fail is *deterministic*: a selector exists, text matches, a row was written, a status code is 200. Those are the RED→GREEN signal at every level, e2e included. **"It looks right" is not deterministic**, so it is *not* part of this gate — it belongs to the [Judge](#the-judge), which compares a screenshot against intent. Determinism gates; aesthetics get a second opinion. Keeping them separate is what stops "looks fine to the model" from ever counting as "done."

## The error set, and what "stuck" means

This is the rule that lets tsforge fix things on its own without looping forever.

- **The error set** = every failure the checks report this cycle, each with a stable key: `tsc` errors (`file:line:code`), eslint/lint-meta violations (`file:line:rule`), and failing tests (`test id`). Its **size** is the count.
- **Progress** = the error set *shrinks* between cycles (count drops, moving toward zero).
- **Stuck (stall)** = a repair cycle (EDIT → VALIDATE) that does **not** shrink the error set — the count is flat, or it's just trading one error for another (oscillation) — for **N consecutive cycles**.

Concrete starting values (tunable, and we'll measure them):

- **N = 3.** Three repair cycles in a row with no net progress → **the stuck handler kicks in** (ask, or escalate — see below).
- **Hard cap = 12 cycles** per chunk regardless, as a backstop.
- **Cheating tripwire** = if an edit weakens or deletes a test assertion to make the gate pass, **stop immediately**. The point of test-first is that the goalpost can't move; this enforces it.

## Getting unstuck — and when to call for help

What the stuck handler does depends on the run's **mode** (set per spec — this *is* the "configurable autonomy" knob):

- **Interactive** — stop and ask you. You're nearby; your judgment is the cheapest fix.
- **Unattended (Ralph loop)** — *never* block on a human. Climb an **escalation ladder**, where each rung is a genuinely *different* approach, not another patch:

  1. **Drop the poisoned reasoning.** Clear the chunk's preserved thinking and re-reason from scratch — a stall usually traces to an early wrong assumption the model keeps reinforcing.
  2. **Reset and re-attempt fresh.** Revert to the chunk's start checkpoint, throw away the broken patches, and re-run RED→EDIT in a fresh context — with the failed attempt recorded as a "this didn't work, because Z" prior. Don't keep building on a wrong foundation.
  3. **Widen context.** Pull in more of the dependency closure, the full failing-test source, and the exact constitution rule (+ its doc) that's failing. Stuck is often just missing context.
  4. **Shrink the cut.** If one task won't converge, it was probably too big — split it into smaller sub-tasks and run those.
  5. **Exhausted** → mark the task `blocked` in the spec, **fire a notification** (below), and **move on to other unblocked tasks** so the loop keeps producing. When nothing unblocked remains, notify "spec stalled" and idle.

### The notification

In unattended mode the human is **async**. When a task is parked `blocked` (or the whole spec stalls), tsforge POSTs to a configured webhook — Slack, Discord, whatever — with the spec + task, the standing error set, which escalation rungs it tried, and a link to the branch/checkpoint. You wake up to *"stuck on task 3, here's exactly where,"* not a frozen process or a silent death. The loop never waits on you; it tells you and keeps going where it can.

This is what makes "set it running overnight" safe: it exhausts *its own* ideas before borrowing yours, and surfaces a clean, specific report instead of thrashing forever or dying quietly.

### Sandboxed by default (unattended)

A loop running for hours with full tool permissions must not be able to harm the host. Unattended runs execute in a **sandboxed container** (Docker): the agent gets full permissions *inside the box*, while your machine, your other repos, and your secrets stay outside it. Fast and bold inside; contained outside.

When it does stop (either mode), it reports *why* — the standing error set + what it tried — so you debug from a clear state, not a mystery.

## The Judge

After the gate is green, a **fresh-context** pass (same model, clean slate) gets the diff + the chunk's `covers:` criteria and is asked to *refute*: "show how this fails to satisfy `A#`, or breaks a constitution rule, or is incomplete." Fresh context matters — it can't inherit the implementer's rationalizations. If it refutes with something concrete, that becomes a new error and we go back to EDIT; if it can't, the chunk passes.

## What if we skip a step? (the honest cut test)

- **Skip RED** → no fixed goalpost; the model defines done as it goes. The whole intent-safety story collapses.
- **Skip the structured error set** → repair has no gradient; the model flails at raw logs.
- **Skip the stall guard** → infinite loops and token burn; the worst failure mode in every comparable agent.
- **Skip the Judge** → gate-green/intent-wrong slips through on the cases tests don't cover.
- **Skip CHECKPOINT** → no safe revert point; one bad chunk can't be rolled back cleanly.

Every step earns its place. None is decoration.

## ELI6

The kid builds one step of the Lego set. **First** he agrees what "this step worked" looks like and checks it *doesn't* work yet (RED). He builds it (EDIT), then pushes to see if it stands (VALIDATE). If it wobbles he fixes it and pushes again (REPAIR) — but if it keeps falling the same way three times, he stops and asks you instead of trying forever (STALL). When it stands, a *second* kid who didn't build it checks it really matches the picture (JUDGE). Then he takes a photo so we can always go back to this exact step (CHECKPOINT), and starts the next one.

## Decisions

1. **N = 3, hard cap = 12** — starting defaults, tunable against the golden tasks.
2. **Escalation order:** drop-thinking → reset & re-attempt → widen context → shrink the cut → notify.
3. **Notify:** Slack + Discord webhooks to start.
4. **Test-approval knob** (interactive only): optional setting to pause for human approval of the RED test before EDIT. Off by default; the cheating-tripwire + Judge cover the rest. (No pause in unattended mode.)
